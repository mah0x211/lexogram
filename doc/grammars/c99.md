# C99 grammar

The built-in grammar of C99 (ISO/IEC 9899:1999). It reads a C source as written, before preprocessing: a directive is a token that the rules skip, and macros are not expanded, so the code outside the directives has the syntax of C99, with [the forms that macros make](c_macro.md) in it (the mixin `lexogram:c_macro`, which the grammar embeds). The rules follow the names of Annex A of the standard. Like every [built-in grammar](../grammar.md#built-in-grammars), it is a sample with no promise of compatibility: copy it with `lexogram.merge` to use it, and see [the changes](#changes) for what changed.

```lua
local lexogram = require('lexogram')
local compiled = assert(lexogram.compile(assert(lexogram.load('lexogram:c99'))))
local result = assert(lexogram.parse(compiled, 'int main(void) { return 0; }'))
```

The sections below follow the top-level fields of `grammars/c99.lua`; [the grammar format](../grammar.md) describes what each field means.

## Metadata

| Field | Value |
|---|---|
| `embeds` | `lexogram:c_macro`: [the forms of macros](c_macro.md) |
| `lexogram` | `2026.11.15.1` |
| `name` | `c99`, the built-in grammar `lexogram:c99` (module `lexogram.grammars.c99`) |
| `version` | `1999-1`: the year of the standard and the revision of the grammar |

## start

`translation_unit`: any number of external declarations. A source of directives and comments only, such as a header that defines macros, is one with none (the standard asks for at least one external declaration).

## tokens

| Token | Definition |
|---|---|
| `identifier` | Letters, digits, `_` and universal character names (`\uXXXX`, `\UXXXXXXXX`), not starting with a digit |
| `number` | An [array of two patterns](../grammar.md#arrays-of-patterns). The first is a preprocessing number: a digit (or a dot and a digit), then digits, letters, `_`, dots and a sign after `e`, `E`, `p` or `P`. The second is the forms of the constants that it must have: an integer constant (decimal, octal or hexadecimal, with the suffixes `u`, `l` and `ll` in either order and case, not `lL`) or a floating constant (decimal with an optional exponent, or hexadecimal with a binary exponent, with the suffixes `f` and `l`). A preprocessing number of another form is an `invalid_token` error: `08`, `1.2.3`, `0x1p`, and `0x1e+1`, which C reads as one preprocessing number |
| `character_constant` | `'c'` and `L'c'`: one or more characters or escapes (`\'`, `\"`, `\?`, `\\`, `\a` `\b` `\f` `\n` `\r` `\t` `\v`, octal escapes of one to three digits, `\x` and hexadecimal digits, universal character names) |
| `string_literal` | `"..."` and `L"..."` with the same escapes; a backslash and a line break (a line splice) may be inside. Adjacent string literals are one operand of `postfix_expression` |
| `space` | Spaces, tabs, vertical tabs, form feeds and line breaks, and a line splice between tokens; not a line break that a directive follows |
| `line_comment` | `//` to the end of the line; a line splice continues it |
| `block_comment` | A delimited token from `/*` to `*/`; an unclosed one is an `unterminated_token` error |
| `directive` | A line break, then a line whose first token is `#` or `%:`, up to the end of the line: with its line splices, its comments (a block comment can go on to other lines, and the directive with it) and its quoted text (a quote that is not closed on its line, as in `#error don't`, runs to the end of the line, and no comment starts inside it) |
| `first_directive` | The same at the start of the source, without the line break (a [leading](../grammar.md#leading) token) |

The fragments `_nondigit`, `_ucn`, `_integer_constant`, `_long`, `_floating_constant`, `_exponent`, `_escape`, `_line_break`, `_blank`, `_directive` and `_directive_body` are the parts of these patterns.

## symbols

The punctuators of C99 that the rules use, 50 literals, among them the digraphs `<:` `:>` `<%` `%>` for `[` `]` `{` `}`. `#`, `##`, `%:` and `%:%:` are read inside directives only; a `#` that is not the first token of its line is an `INVALID` token.

## keywords

The 37 keywords of C99, from `auto` to `_Imaginary`.

## skip

`space`, `line_comment`, `block_comment`, `directive` and `first_directive`.

## leading

`first_directive`.

## rules

Rules with events:

| Rule | Pattern (simplified) |
|---|---|
| `translation_unit` | `external_declaration*` |
| `external_declaration` | `function_definition / declaration` |
| `function_definition` | specifiers, `declarator`, `declaration*`, `compound_statement` |
| `declaration` | specifiers, `init_declarator_list?`, `";"` |
| `storage_class_specifier` | `"typedef"`, `"extern"`, `"static"`, `"auto"` or `"register"` |
| `type_specifier` | a type keyword, `struct_or_union_specifier`, `enum_specifier` or `typedef_name` |
| `typedef_name` | `identifier` |
| `type_qualifier` | `"const"`, `"restrict"` or `"volatile"` |
| `function_specifier` | `"inline"` |
| `init_declarator_list` | `init_declarator ("," init_declarator)*` |
| `init_declarator` | `declarator ("=" initializer)?` |
| `struct_or_union_specifier` | `("struct" \| "union") identifier? ("{" struct_declaration+ "}")?` |
| `struct_declaration` | specifiers and qualifiers, `struct_declarator_list`, `";"` |
| `struct_declarator_list` | `struct_declarator ("," struct_declarator)*` |
| `struct_declarator` | `declarator (":" constant_expression)? \| ":" constant_expression` |
| `enum_specifier` | `"enum" identifier? ("{" enumerator ("," enumerator)* ","? "}")?` |
| `enumerator` | `identifier ("=" constant_expression)?` |
| `declarator` | `pointer? direct_declarator` |
| `direct_declarator` | `identifier` or `"(" declarator ")"`, then array suffixes and at most one `function_suffix` |
| `pointer` | `("*" type_qualifier*)+` |
| `function_suffix` | `"(" parameter_type_list? ")"` |
| `parameter_type_list` | `parameter_declaration ("," parameter_declaration)* ("," "...")?` |
| `parameter_declaration` | specifiers, then `declarator` or `abstract_declarator` (optional) |
| `type_name` | specifiers and qualifiers, `abstract_declarator?` |
| `abstract_declarator` | `pointer direct_abstract_declarator? \| direct_abstract_declarator` |
| `direct_abstract_declarator` | `"(" abstract_declarator ")"`, array suffixes and `function_suffix` |
| `initializer` | `assignment_expression \| "{" initializer_list ","? "}"` |
| `initializer_list` | `designation? initializer ("," designation? initializer)*` |
| `designation` | `designator+ "="` |
| `designator` | `"[" constant_expression "]" \| "." identifier` |
| `statement` | one of the six kinds below |
| `labeled_statement` | `identifier ":" statement`, `"case" constant_expression ":" statement`, `"default" ":" statement` |
| `compound_statement` | `"{" block_item* "}"` |
| `block_item` | `declaration / statement` |
| `expression_statement` | `expression? ";"` |
| `selection_statement` | `if` (an `else` belongs to the nearest `if`) and `switch` |
| `iteration_statement` | `while`, `do ... while` and `for` (with a declaration or an expression first) |
| `jump_statement` | `goto`, `continue`, `break` and `return` |
| `expression` | `assignment_expression ("," assignment_expression)*` |
| `assignment_expression` | terms and binary operators, then `assignment_operator assignment_expression` or `conditional` |
| `conditional` | `"?" expression ":" assignment_expression` |
| `constant_expression` | terms and binary operators, then `conditional?` |
| `assignment_operator` | `=`, `*=`, `/=`, `%=`, `+=`, `-=`, `<<=`, `>>=`, `&=`, `^=`, `\|=` |
| `binary_operator` | `*`, `/`, `%`, `+`, `-`, `<<`, `>>`, `<`, `>`, `<=`, `>=`, `==`, `!=`, `&`, `^`, `\|`, `&&`, `\|\|` |
| `unary_operator` | `&`, `*`, `+`, `-`, `~`, `!` |
| `sizeof_expression` | `"sizeof" ("(" type_name ")" / term)` |
| `cast_expression` | `"(" type_name ")" term` |
| `postfix_expression` | an operand (`identifier`, a constant, string literals, `compound_literal` or `"(" expression ")"`) and its suffixes (`[...]`, `(...)`, `.` and `->` with a name, `++`, `--`) |
| `compound_literal` | `"(" type_name ")" "{" initializer_list ","? "}"` |
| `argument_expression_list` | `assignment_expression ("," assignment_expression)*` |

The rules whose names start with `_` group alternatives and produce no events (`_struct_declarators` and `_strings` are rules of their own so that a [mixin](../grammar.md#mixins) can replace them); `declaration-specifiers` and `specifier-qualifier-list` of the standard are no rules of their own, so the specifiers are the first children of a declaration.

## Which identifiers name types

Whether an identifier names a type decides how C is parsed, and it depends on declarations that this grammar does not track. An identifier may be a type specifier (`typedef_name`), and the forms that both readings fit are told apart by [trials](../grammar.md#how-rules-are-applied) (ordered choices), so that the readings of common code are the right ones:

- **Specifiers of a declaration**: an identifier after a specifier is tried first as the start of the declarators with the rest of the declaration (up to its `;`, or its body for a function definition), then as a type name. `T x;` declares `x` of type `T`, and `MACRO T *x;` reads `MACRO` and `T` as types.
- **Parameter declarations**: an identifier before the first type specifier is a type name; after it, the identifier is tried as the declarator first: `int f(const T x)`.
- **Declarators**: a function declarator is followed by no other suffix (a function returns no function or array), and a declarator that is an identifier in parentheses is followed by a suffix. `int (f)(void)` declares `f`, and `LUA_API lua_Number (lua_tonumberx) (lua_State *L)` declares `lua_tonumberx`.
- **Block items**: a block item is tried as a declaration first. `T *p;` declares `p`, and `f(x);` is a call: as a declaration, `(x)` would need a suffix.
- **Casts**: a cast is tried before a parenthesized expression: `(T)x` is a cast.
- **sizeof**: `sizeof` is tried with a type name first: `sizeof(x)` reads `x` as a type name.

Where the identifier is not a type, these choices give the other reading: `a * b;` declares `b` of type `a`, `(a) - b` casts `-b` to `a`, `sizeof (a)[0]` is an error, and `f(x)(y);` declares `x`. The structure of such code, rare in practice, is that of the reading chosen; the sources accepted are the same, except for `sizeof` (see [the differences](#differences-from-c99)).

## Expressions

An expression lists its terms and operators in order, without precedence; a consumer applies the precedence of C. A term is a `postfix_expression`, after any unary operators, `++`, `--`, `sizeof` or casts (`cast_expression` and `sizeof_expression` hold the term they apply to). From high to low:

| Operators | Associativity |
|---|---|
| suffixes `[]` `()` `.` `->` `++` `--`, compound literals | left |
| unary `++` `--` `&` `*` `+` `-` `~` `!`, `sizeof`, casts | right |
| `*` `/` `%` | left |
| `+` `-` | left |
| `<<` `>>` | left |
| `<` `>` `<=` `>=` | left |
| `==` `!=` | left |
| `&` | left |
| `^` | left |
| `\|` | left |
| `&&` | left |
| `\|\|` | left |
| `?:` (`conditional`) | right |
| assignment (`assignment_operator`) | right |
| `,` (in `expression`) | left |

An assignment or a conditional ends an `assignment_expression`; its left side is not checked to be a unary expression (`a + b = c` is accepted), and the last operand of a conditional is an `assignment_expression`. A `constant_expression` has no assignment.

## Differences from C99

The grammar describes the syntax only, of a source before preprocessing. It accepts every source that has the syntax of C99 after preprocessing without changing it, except for the forms below, and some sources that C99 rejects:

- **Forms of macros**: [the forms that macros make](c_macro.md) are accepted, though they have no syntax of C99: a member declared by a macro (`CommonHeader;`), a type name as a macro argument (`cast(char, c)`), and names and calls of macros next to string literals (`"a" LUA_QS "b"`). A source with the syntax of C99 is read as without them.
- **Constraints**: the checks that are not syntax are not made: the types of operands, lvalues, the combinations of type specifiers (`MACRO T` reads both as types), implicit `int`, and the declarations of labels and identifiers.
- **Identifier lists**: the parameters of a function declarator with an identifier list (`int f(a, b) int a, b; { }`) are read as parameter declarations of type names.
- **sizeof of a parenthesized operand with a suffix**: `sizeof (a)[0]` and `sizeof (T){ 1 }` are syntax errors, as `sizeof (a)` and `sizeof (T)` are taken with a type name first (trying the expression first would read `sizeof(T) * n` as `sizeof((T) * n)`); write `sizeof((a)[0])`.
- **Lexical forms not supported**: trigraphs; a line splice inside a token other than a string literal, a comment or a directive; a comment before the `#` of a directive on its line.

## Results on real sources

The grammar was run on the C sources of Lua 5.1.5, 5.2.4, 5.3.6, 5.4.8 and 5.5.1 (`src/*.c` and `src/*.h`, 295 files, 3.36 MB) on 2026-11-19. 262 files (88.8%) parse without a syntax error, and their event arrays cover their sources exactly; without [the forms of macros](c_macro.md), 173 files parse. The other 33 fail at the first of these forms, which the macros of Lua make and which have no C99 syntax before preprocessing:

| First error | Files | Example |
|---|---:|---|
| A statement or a declaration as a macro argument | 12 | `LUAI_DDEC(const lu_byte luai_ctype_[UCHAR_MAX + 2];)` |
| An operator as a macro argument | 10 | `intop(+, v1, v2)` |
| Names of macros next to each other | 6 | `LUA_PATH_SEP LUA_PATH_SEP` |
| A macro used as a statement keyword | 1 | `vmdispatch (GET_OPCODE(i)) {` |
| A member declared by a macro without its `;` | 1 | `numfield` |
| Conditional compilation and GNU extensions | 3 | C++ code in an `#if` branch, `&&L_OP_MOVE` |

## Performance

Measured on the 51 files of Lua 5.4.8 that parse, concatenated and repeated to 2.63 MB (best of 5 in one process, CPU time, 2026-11-19, local machine). Load and compile is the time of the first `lexogram.load` of the grammar, which checks it, and of `lexogram.compile`. On LuaJIT the speed differs between processes; the range of five processes is shown.

| Runtime | Load and compile | Tokenize | Parse to the event array |
|---|---|---|---|
| Lua 5.1 | 0.64 s | 4.9 MB/s | 1.3 MB/s |
| Lua 5.4 | 0.48 s | 6.8 MB/s | 1.8 MB/s |
| Lua 5.5 | 0.46 s | 6.7 MB/s | 1.8 MB/s |
| LuaJIT 2.1 | 0.27 to 0.37 s | 92 to 96 MB/s | 13 to 16 MB/s |

Most of the compile time is the automaton of the tokens (482 states), whose directives hold comments and quoted text, and the analysis of two tokens ahead. Parsing is slower than for the Lua grammars (2.3 MB/s on Lua 5.1) because of the trials: a declaration is tried before each block item that starts with a name, a function definition before each external declaration, and a cast before each parenthesized expression.
